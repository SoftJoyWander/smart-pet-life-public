# 智能便便垃圾桶連線與協定設計

產品定義與使用流程見 [2026-08-27 決策摘要](./CHAT_LOG_2026-08-27.md)。本文件補上該次決策**沒有寫下原因**的部分，並作為 BLE 協定的落腳處。

狀態：連線方式已定案；BLE GATT 契約與韌體尚未實作。

硬體接線見 [SMART_BIN_WIRING.md](./SMART_BIN_WIRING.md)。

## 為什麼只用 BLE，不讓手機連裝置的 Wi-Fi

2026-08-27 的決策寫了「不需要 Wi-Fi 場地帳號」，但沒有記錄理由。理由本身比結論重要，因為 Wi-Fi 看起來比 BLE 好寫，日後很容易有人重新提案。

**手機必須同時和兩邊通訊。** 整個授權流程是交錯的：

```
手機 ← BLE →  垃圾桶      取得設備挑戰碼
手機 ← 行動網路 → Supabase  驗證帳號、寵物、observation 與設備狀態，取得一次性授權
手機 ← BLE →  垃圾桶      下達綁定 nonce 的指令
```

若裝置改開 Wi-Fi 熱點（SoftAP）供手機連線，**手機連上之後就失去外網**，中間那一步無法完成。手機不再能作為雲端閘道器，而「手機當閘道」正是這個設計不需要在垃圾桶上放 Wi-Fi 帳號、4G 門號或 GPS 的前提。

作業系統有時會在 Wi-Fi 無外網時保留行動數據給 App 使用，但該行為在 iOS 與 Android 之間不一致、也隨版本變動，不能作為設計基礎。

BLE 與行動網路可同時運作，沒有這個衝突。

**次要理由**：使用者需手動切換 Wi-Fi（iOS 尤其繁瑣）、Wi-Fi 耗電明顯高於 BLE、裝置需維護 DHCP 與 HTTP 服務，增加攻擊面。

## Wi-Fi 唯一保留的可能用途

現場維護模式：技師在裝置旁臨時開啟熱點以更新韌體或讀取詳細日誌。該情境不需要雲端連線，因此不受上述限制。**第一版不實作。**

## 裝置上不放螢幕

所有狀態與錯誤都在手機端呈現。裝置只負責執行指令與回報事件，判斷與顯示交給 App。

QR 只包含設備 ID、內容固定且不含秘密，因此**印製貼紙即可**，不需要動態顯示：貼紙更便宜、不耗電、裝置斷電時仍可掃描。

曾評估以 OLED 顯示動態 QR 以強化現場證明，結論是與既有的 BLE 近場挑戰重複，增益有限，且戶外強光下小螢幕辨識率低、外殼需開透明窗並處理防水、抗 UV 與結露。

開發階段若需觀察狀態機，以序列埠輸出即可。

### 特徵值

| 特徵值 | UUID 前綴 | 屬性 | 用途 |
| --- | --- | --- | --- |
| `device_info` | `00011...` | read | 裝置 ID、韌體版本、協定版本、能力旗標 |
| `status` | `00021...` | read, notify | 目前狀態與錯誤碼 |
| `challenge` | `00031...` | read | 讀取即產生新的 nonce 與計數器 |
| `command` | `00041...` | write | 後端簽章過的一次性指令 |
| `event` | `00051...` | notify | 即時事件，**未簽章，只供 App 更新畫面** |
| `receipt` | `00061...` | read, notify | 裝置簽章的完整事件回執，**後端只信任這個** |

不使用 BLE 配對或綁定。公共設備會被大量帳號連線，bonding 是為個人配對設計的，會累積綁定紀錄並在換手機時失效。安全性來自應用層的 HMAC 與 nonce，不是 BLE 鏈路加密。

### 為什麼事件與回執分開

`event` 讓 App 立即更新畫面，不必等簽章；`receipt` 是裝置對整段事件鏈的單一簽章，後端只根據它建立設備確認紀錄。

這個分法同時解決一個實務問題：使用者手機沒電、走出距離或 App 被系統關閉時，事件通知會中斷。**裝置會保留最後一份回執直到下一次 session 開始**，App 之後重新連線仍可取回並補送後端。若只靠即時事件，這種情況會永遠遺失投放證明。

## 安全模型

### 金鑰

每台裝置有唯一的對稱金鑰 K，燒錄時寫入 NVS，並保存在 Supabase 的非公開 schema。裝置不會輸出 K，App 永遠拿不到 K。

App 因此無法偽造指令，也無法偽造回執。這是「App 不能自行把任務改成完成」這條規則的實際執行方式 —— 只靠 App 端自律不算數。

### 防重放

裝置維護單調遞增計數器，保存在 NVS，斷電後從上次的值繼續。指令必須帶上裝置當前的 nonce 與計數器，且：

- nonce 只在被有效指令使用時作廢；未使用的 nonce 可被新的取代，因此使用者取消操作不會浪費授權
- 計數器不接受倒退
- 每個 nonce 只能用一次

### 時間

**裝置沒有 RTC 也沒有網路，不知道現在幾點。** 因此：

- 絕對時效（任務 15 分鐘、投放 10 分鐘）由**後端**以牆鐘判斷
- 相對時效（解鎖後自動上鎖）由**裝置**以自己的計時器判斷，指令中帶 `window_seconds`
- 防重放不依賴時間，只依賴計數器

## 使用流程

```text
1. 使用者按「解鎖投入口」
2. App 顯示確認：解鎖後有 N 秒可投入，確定現在就投嗎
3. 使用者確認
4. App 讀 challenge，取得 nonce 與計數器
5. App 送後端：device_id、nonce、計數器、session
6. 後端核對帳號、寵物、observation、裝置狀態與時間窗
   計算 MAC = HMAC-SHA256(K, 指令欄位 ‖ device_id)，截斷為 128 bit
7. App 寫入 command
8. 裝置以自己的 K 驗證，檢查 nonce 未使用、計數器未倒退
9. 裝置解鎖並開始計時，逐步發出 event
10. 裝置產生簽章 receipt，App 讀取後轉送後端
11. 後端驗證簽章，只有完整鏈才建立設備確認紀錄
```

**授權必須在步驟 3 之後才取得。** 後端簽發的指令有有效期，若先取授權再等使用者確認，使用者猶豫過久會導致指令過期，產生「明明按了確認卻說授權失效」這種難以理解的錯誤。

App 端會顯示倒數，但**裝置的計時器才是權威**；兩者會有數百毫秒漂移，文案不得讓使用者以為畫面上的秒數精確。

逾時後可在投放窗內重新申請解鎖，取得新的一次性授權。不提供「延長」，重新解鎖已足夠且不需要額外協定。

`window_seconds` 由裝置端設定，第一版為 30 秒，**不寫死在程式碼**。實際秒數需以真人測試調整：使用者可能一手提著袋子、投入口可能略卡、長者動作較慢。

## 有效的事件鏈

只有依序完整收到下列事件，才算一次成功投放：

```text
unlock_confirmed → hatch_closed → latch_locked
```

領取袋子、模型候選為 `present`、或單純下達解鎖指令，**都不等於成功投放**，也不發放積分。

### 為什麼沒有 hatch_opened（2026-09-18 修訂）

原本的鏈是四段，中間有一個獨立的 `hatch_opened`。實作時發現不需要，而且不需要蓋子感測器就能成立。

**斜舌只有在不處於鎖孔裡的狀態下，才會被關門時的斜面壓回去。** 蓋子從未開過的話，鎖舌一直在鎖孔裡，沒有任何東西能壓它。因此「鎖舌的第二次縮回」同時證明兩件事：蓋子曾經開過，而且正在關上。`hatch_opened` 由 `hatch_closed` 邏輯上隱含，不必單獨觀測。

這讓裝置只靠四線鎖內建的回饋接點就能產生完整事件鏈，省掉一個感測器與兩條線。2026-09-18 已在實體 ESP32-C3 上以按鈕模擬驗證完整三段鏈。

**代價**：分不出「蓋子卡住沒開」與「開著但人走了」—— 兩者都是沒有第二次縮回，只能一起逾時處理。兩種都不是成功投放，後端處理方式相同，因此可以接受。

**已知破口**：有人用手指把鎖舌壓回去，可以偽造「蓋子關上了」。這不在威脅模型內 —— HMAC 與計數器防的是「App 遠端自稱完成」這種可規模化的攻擊；跑到垃圾桶前面壓鎖舌，還不如直接投一包東西進去。

### 開鎖是脈衝，不是持續通電（2026-09-18 修訂）

原先的設計讓線圈持續通電到投放窗結束。那是錯的：**斜舌要彈出來卡進鎖孔才叫上鎖，而線圈通電期間鎖舌被拉住縮回 —— 持續通電會主動阻止蓋子上鎖。** 使用者十秒投完，卻得按著蓋子等到三十秒斷電才能真正關上。

改為：通電 → 等鎖舌縮回 → 續電一小段讓蓋子彈開並使鎖舌脫離鎖孔 → 斷電。之後任何時候關上蓋子，斜舌都會自動卡上。這也是快遞櫃與外送櫃的既有模式，使用者已經熟悉。

`window_seconds` 的意義隨之改變：**從「通電多久」變成「多久沒關上就視為未完成」**。欄位與位元格式未動，語意已改。

蓋子還開著期間，裝置每十秒發一次提醒事件供 App 顯示。

## 錯誤碼與模擬器情境對應

模擬器已定義的失敗情境，協定必須逐一對應：

| 模擬器情境 | 由誰判定 | 對應處理 |
| --- | --- | --- |
| `invalid_qr` | 後端 | 裝置 ID 不存在或已停用 |
| `full` | 裝置 | `status` 回報滿載，後端拒絕發授權 |
| `no_bags` | 裝置 | 同上 |
| `maintenance` | 後端 | 裝置標記維護中 |
| `busy` | 裝置 | 已有進行中的 session |
| `network_offline` | App | 無法取得授權，不送出任何 BLE 指令 |
| `bag_jam` | 裝置 | 出袋感測器未在時限內確認 |
| `unlock_timeout` | 裝置 | `window_seconds` 內未偵測到開門 |
| `hatch_stuck` | 裝置 | 偵測到開門但未在時限內關閉 |
| `lock_failed` | 裝置 | 鎖舌感測器未回報上鎖 |

## 尚未決定

- **金鑰佈建流程。** 每台裝置的 K 必須不同且不得進入 Git。需要一次性佈建工具與紀錄方式。
- **計數器溢位。** 32 位元在此用量下不會用盡，但是否需要處理仍待確認。
- **離線投放。** 使用者在無訊號處能否先投放、事後補回報。會大幅增加複雜度，第一版傾向不支援。
- **同時服務多位使用者。** 模擬器已有 `busy` 情境，是否需要排隊尚未決定。
- 韌體實作與 Supabase schema，兩者都待協定定案後再進行。
