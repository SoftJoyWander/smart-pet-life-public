## 1. 決策摘要

Smart Pet Life 的近期定位是「寵物生活、共同照護與就醫資料協作平台」，不是遠距醫療設備平台。現有飼主 App 保留飲食、飲水、排泄、遛狗、提醒、照片及家庭共同照護；新增獸醫院 Web Portal，讓已驗證的院方人員在飼主授權後上傳就醫檔案與檢查數據。

第一階段不依賴居家醫療設備、藍牙量測器、醫療設備閘道器或院內系統 API。醫院以瀏覽器手動建立就醫事件、上傳原始報告及填寫結構化結果；院內系統整合留到流程穩定後。

平台只保存、整理、追溯及分享資料，不自行確定診斷、開立處方、調整療程或把趨勢冒充獸醫判斷。

## 2. 範圍與非範圍

### 2.1 第一階段範圍

- 飼主與共同照護者繼續使用目前的生活照護 App。
- 建立經驗證的獸醫院機構及院方人員帳號。
- 飼主以短效、一次性授權碼或 QR code 連結指定寵物與醫院。
- 院方建立就醫事件，上傳 PDF／圖片等原始檔案。
- 院方輸入檢查項目、數值、單位、院方參考區間及原始旗標。
- App 顯示醫院來源、發生時間、上傳時間、版本及修正狀態。
- 生活分享與醫療內容分區；醫療內容預設不進入公開或家庭動態。
- 對敏感資料的查看、下載、上傳、修正、授權及撤權留下稽核紀錄。

### 2.2 第一階段非範圍

- 居家或院內醫療設備自動傳值。
- BLE、Wi-Fi 或其他醫療設備管理。
- 取代獸醫院既有診療／個案管理系統。
- 平台自行產生疾病診斷、處方或治療建議。
- 未經院方確認的 OCR 結果直接成為正式數據。
- 將營運中的醫療文件自動用於 AI 訓練。
- 公開社群顯示病例、處方、檢查數值或原始文件。

## 3. 角色與權限

| 角色 | 生活資料 | 醫療資料 | 管理能力 |
| --- | --- | --- | --- |
| 飼主 `owner` | 完整管理 | 完整查看；決定分享與授權 | 管理照護者、醫院連結及醫療查看權 |
| 生活編輯者 `editor` | 可新增與編輯 | 預設不可看；需飼主另授權 | 不可授權醫院或其他人 |
| 生活檢視者 `viewer` | 可查看 | 預設不可看；需飼主另授權 | 無 |
| 醫院管理者 `clinic_admin` | 不可預設查看 | 管理該院人員與該院提交紀錄 | 驗證人員、停權與稽核 |
| 院方上傳人員 `clinic_staff` | 只能看授權範圍 | 建立草稿、上傳文件、輸入結果 | 不可標示獸醫覆核 |
| 獸醫師 `veterinarian` | 只能看授權範圍 | 可在資格與身分證據存在時覆核院方紀錄 | 修正須建立新版本，不覆寫舊版 |
| 平台支援人員 | 預設不可查看內容 | 僅經核准的最小必要支援存取 | 所有敏感操作均需稽核 |

`veterinarian_reviewed` 只能在保存獸醫師識別、所屬機構、覆核時間與被覆核版本後使用。一般院方上傳只能標示 `clinic_submitted`，不能自動升級為獸醫師確認。

## 4. 服務邊界與資料流

```text
飼主／共同照護 App
  ├─ 生活紀錄、遛狗、提醒、家庭動態
  ├─ 顯示就醫履歷、文件及檢查數據
  └─ 建立／撤銷醫院及照護者授權
                  │ HTTPS
                  ▼
平台 API、Auth、RLS、授權與稽核
  ├─ 寵物與共同照護
  ├─ 獸醫院機構及人員
  ├─ 就醫事件及檢查結果
  ├─ 私人文件中繼資料
  └─ 通知及短效下載
          │                    │
          ▼                    ▼
PostgreSQL                 私人 Storage
          ▲
          │ HTTPS
獸醫院 Web Portal
  ├─ 一次性授權連結
  ├─ 就醫事件與文件上傳
  └─ 結果輸入、確認與修正

院內系統 ── 未來受控 API／批次匯入 ──> 獸醫院 Web Portal／平台整合層
```

生活資料、醫療資料與未來社群內容共用寵物身分，但使用不同權限界線。社群服務只能收到使用者明確選擇的生活內容，不得從醫療資料庫自動投影詳細內容。

## 5. 核心流程

### 5.1 醫院與人員啟用

1. 平台建立待驗證醫院資料。
2. 核驗機構名稱、聯絡方式及負責人；具體證據與核驗負責人仍為營運 `TBD`。
3. 醫院管理者邀請院方人員並分配最小角色。
4. 人員離職、停權或醫院失效時，立即禁止新存取；既有稽核紀錄保留。

### 5.2 飼主授權醫院連結寵物

1. 飼主在 App 選定寵物與欲分享的範圍。
2. 平台產生短效、一次性授權碼或 QR code，不包含 JWT、醫療資料或永久識別秘密。
3. 院方登入後兌換授權，畫面只顯示確認錯誤寵物所需的最少資訊。
4. 飼主收到連結完成通知，可查看有效期、範圍並撤銷後續存取。
5. 過期、已使用、寵物不符或院方帳號無效時拒絕兌換，且不洩漏其他寵物資訊。

### 5.3 就醫與文件上傳

1. 院方在已授權寵物下建立就醫事件，保存實際就醫時間、時區、院方及建立者。
2. 文件先建立上傳草稿，通過類型、大小、路徑及惡意內容檢查後才可發布。
3. 每個檔案都有獨立中繼資料、內容雜湊、版本、上傳者與來源；不可只把路徑陣列塞進一般生活紀錄。
4. 原始文件發布後通知飼主；失敗時保留可重試草稿，不顯示為已完成。
5. 更正以新版本或 `supersedes_id` 關聯舊版，不直接覆寫已發布證據。

### 5.4 檢查數據

1. 每份檢查報告連結一個就醫事件及一份原始文件（若院方有提供）。
2. 每個結果分別保存項目名稱／代碼、值、原始單位、標準化單位（若可安全轉換）、院方參考區間、原始旗標、檢體及方法。
3. 缺少值、單位或參考區間時保存為未知，不製造精確度。
4. OCR 或匯入只能建立草稿；院方確認後才成為 `clinic_submitted`。
5. App 可忠實顯示院方的高低旗標，但不得自行把單一結果轉成疾病名稱或治療建議。

### 5.5 飼主自行上傳

飼主若自行掃描紙本報告，來源固定為 `owner_uploaded_unverified`。即使文件看似有醫院名稱，也不得標示 `clinic_submitted` 或 `veterinarian_reviewed`；後續可由已驗證院方建立確認版本並連結原文件。

## 6. 資料來源與時間語意

| 來源代碼 | 意義 | 可否代表正式院方資料 |
| --- | --- | --- |
| `owner_reported` | 飼主自行輸入 | 否 |
| `caregiver_reported` | 共同照護者輸入 | 否 |
| `owner_uploaded_unverified` | 飼主自行上傳文件 | 否 |
| `clinic_submitted` | 已驗證醫院帳號提交 | 是，僅代表院方提交 |
| `veterinarian_reviewed` | 具證據的獸醫師覆核 | 是 |
| `system_derived` | 平台摘要、格式轉換或趨勢 | 否 |
| `device_measured` | 未來設備量測 | 第一階段停用 |

每個事件至少分開保存：

- `occurred_at`：實際就醫、採檢或報告事件時間。
- `recorded_at`：院方或飼主輸入時間。
- `received_at`：平台收到資料的伺服器時間。
- `timezone`：事件所在地時區。
- `created_by`／`source_type`：建立者及來源。
- `schema_version`：資料契約版本。
- `supersedes_id`：修正或取代的前一版本。

### 7.3 與現有資料的相容策略

- 目前 `care_record_kind = medical` 在 App 中實際代表驅蟲，不能直接改稱正式就醫。
- 部署前核對時 `care_record_kind = medical` 與 `medical_file_paths` 均為 0 筆；本階段仍不改動列舉，避免破壞既有 App 的驅蟲語意。
- 正式就醫使用獨立 `medical_visits`，不把病例生命週期塞進 `care_records`。
- 目前 `care_records.medical_file_paths[]` 保留相容但停止作為新病例設計；未來以一檔一列的 `medical_documents` 取代。
- 既有 `pet-media` 維持私人；正式病例使用獨立且私人的 `medical-media` bucket。
- 所有變更採新增 migration，不改寫或刪除既有 migration 歷史。

## 8. RLS、Storage 與安全邊界

### 8.1 RLS 原則

- 飼主可讀自己寵物的醫療資料並管理分享授權。
- 共同照護者只有在有效 `medical_access_grants` 存在時才能讀取對應範圍。
- 院方人員必須同時具備有效人員身分、有效醫院、有效寵物授權及符合角色的操作權。
- 醫院預設只能讀寫該院建立的資料；查看其他醫院歷史須有飼主另行分享的明確範圍。
- 行動端及醫院前端不得直接寫入稽核表、獸醫資格狀態或已覆核旗標，須由受控 RPC／後端處理。
- 匿名使用者及無關登入者不得以 ID 猜測取得任何資料。

### 8.2 Storage 原則

- 所有病例與檢查文件使用私人 bucket。
- `medical-media` 目前限制單檔 25 MiB，允許 PDF、JPEG、PNG、WebP、HEIC 與 HEIF；惡意內容掃描仍須由後端工作流程完成後才能發布。
- 物件路徑至少綁定 owner、pet、visit 及 document ID，不信任前端任意提供路徑。
- 檔案下載使用短效簽名網址或經驗證串流；簽名網址不回寫資料庫。
- 限制 MIME、大小與允許副檔名；伺服器端驗證實際內容類型並進行惡意檔案掃描。
- 計算內容雜湊以偵測重複與確認版本，但雜湊不是權限憑證。
- 圖片清除不必要 EXIF；若文件含飼主姓名、電話、地址或帳務資料，UI 應提示其可能包含個資。

### 8.3 稽核

至少稽核：授權建立／撤銷、醫院人員變更、文件上傳／下載／發布、檢查結果確認、版本修正、管理支援存取及匯出。一般生活頁面載入可依風險與成本決定是否彙總稽核，不能把敏感內容寫入日誌。

## 9. App 資訊架構與狀態

### 9.1 飼主 App

- 首頁：保留今日照護、提醒、生活摘要及共同照護動態。
- 紀錄：保留生活時間軸，不重複放置醫療中心入口；就醫事件若進入生活摘要，只顯示中性資訊。
- 底部「醫療」頁籤直接進入醫療中心；目前分為「就醫檔案」與「檢查數據」，顯示目前寵物、來源、時間、版本、原始值、單位、院方參考範圍及旗標。
- 我的／寵物設定：醫院連結、醫療查看權及資料請求尚待實作。
- 公開或家庭分享：預設只分享生活內容；醫療內容必須逐次明確選擇且顯示接收對象。

### 9.2 醫院 Portal

- 待授權：輸入或掃描一次性碼。
- 寵物工作區：只顯示授權範圍及院方既有提交。
- 就醫編輯：草稿、驗證失敗、上傳中、待發布、已發布、已修正。
- 文件：上傳進度、格式錯誤、重複提示、惡意內容拒絕及重試。
- 檢查結果：手動輸入／匯入草稿、欄位驗證、院方確認及修正理由。
- 人員管理：邀請、角色、停權、離職及操作紀錄。

### 9.3 必備狀態

兩端均需處理載入、空資料、部分資料、離線／網路錯誤、過期授權、權限不足、檔案處理中、上傳失敗、重複提交、已被修正、通知失敗與可重試狀態。不得先在 UI 顯示「院方已發布」再等待伺服器確認。

## 10. 獸醫安全與顯示規則

- 原始報告、院方輸入、飼主描述及系統摘要分開顯示。
- 參考區間與高低旗標忠實顯示院方原值，不由平台臆造或跨實驗室套用。
- 趨勢只描述變化，例如「較前次增加」，不宣稱病因或診斷。
- 用藥內容保留院方／處方來源、劑量、單位、途徑、時間及有效日期；不由平台自行修正含糊指示。
- 若院方上傳文字包含緊急指示，平台只忠實呈現並提供聯絡醫院入口；通用緊急警示使用經審查的受控文案。
- 沒有可驗證獸醫師身分時使用「醫院提供」或「等待專業複核」，不得顯示「獸醫師確認」。

## 11. 同意、保留、刪除與區域治理

- 服務營運、醫院分享、公開社交、行銷及 AI 訓練是不同目的，不共用一個同意開關。
- 醫院授權保存範圍、政策版本、語言、授予及撤銷時間；撤銷只阻止未來存取，不虛構已下載資料已被遠端刪除。
- 病例、檢查、帳號、稽核與備份的保留期限目前均為 `TBD`，需依用途、醫院責任、法規、風險與核准負責人決定。
- 使用者刪除平台帳號、撤銷分享及醫院依法／依契約保存原始紀錄可能是不同流程，須在上線前由合格法律顧問與合作醫院確認。
- 現有 Supabase 新加坡區域造成跨境資料流；台灣與中國大陸上線前須分別完成資料類別、來源、目的、接收者、區域、權利流程及供應商審查。
- 醫療文件不得預設進入模型訓練。未來若使用，須有獨立、特定、版本化、可撤回且可稽核的同意與資料血緣；醫院或其他權利人的授權也需另行確認。

## 12. 實作階段與驗證

### 12.1 建議階段

1. 文件與決策：確認首發地區、犬／貓範圍、醫院驗證責任、文件類型及分享權限。
2. 資料庫：以新增 migration 建立機構、授權、就醫、文件、結果、版本及稽核模型。
3. 飼主 App：唯讀醫療中心已完成；下一步建立分享權限與受控下載閘道，不改動生活核心流程。
4. 醫院 Portal：完成登入、授權兌換、上傳、數據輸入、發布與修正。
5. 試點：以少量合作醫院手動上傳驗證流程，再評估 OCR 或院內系統整合。

### 12.2 驗收測試

- 飼主、具醫療授權的照護者、無醫療授權照護者、無關登入者及匿名使用者的讀寫結果正確。
- 醫院有效／停權人員、不同醫院及過期／撤銷授權均正確阻擋。
- 一次性碼不能重放，錯誤碼不洩漏寵物或帳號是否存在。
- 文件無法以公開網址取得，且不能跨 pet／visit 猜測路徑。
- 上傳中斷可安全重試，不產生重複發布紀錄。
- 檢查數值保留原值、單位、參考區間、旗標、時間及來源。
- 修正不覆寫原版；飼主能辨認最新版本與修正原因。
- 飼主上傳永遠不會被誤標成院方或獸醫師確認。
- 生活動態及公開分享不會自動帶出醫療詳細內容。
- 繁體／簡體長字串、大字體、VoiceOver／TalkBack、窄螢幕、離線及慢速上傳均可理解與恢復。

## 13. 上線前待決策

- 首發是否只支援犬，或同步完成犬／貓資料約束與 UI。
- 首發服務地區及資料落地／跨境方案。
- 誰負責驗證醫院與獸醫師身分，以及接受哪些證據。
- 醫院可見的歷史範圍、授權有效期及緊急存取是否存在。
- 首發接受的文件類型、大小、惡意檔案掃描及 OCR 供應商。
- 不同醫療資料及稽核資料的保留、匯出、刪除與法律保全政策。
- 「生活社交」首發只限私人共同照護，或包含公開社群；若包含公開社群，需另做內容治理與安全設計。
