## 1. 產品定位

Smart Pet Life 是以寵物日常生活、共同照護與就醫資料協作為核心的平台。現階段的飼主 App 讓飼主及共同照護者可靠地記錄、查看與修正飲食、飲水、排泄、預防照護、用藥及遛狗資料，並以每日摘要和趨勢協助使用者察覺值得留意的變化。

下一階段規劃獸醫院 Web Portal，由已驗證院方在飼主授權後上傳就醫檔案及檢查數據。平台只提供生活紀錄、資料保存、提醒、趨勢、分享與來源追溯，不提供確定診斷、處方或替代獸醫師判斷。另有「照片中是否存在便便」辨識與智慧垃圾桶流程原型，以及只支援犬隻的協尋 MVP。便便模型只回傳未校準分數及原型路由；犬隻 Re-ID 已建立實際 baseline artifact，並接通測試 Supabase、Edge worker 與台灣 Cloud Run 的 shadow 資料流，但台灣實景驗證、公開候選啟用與推播尚未完成。第一階段不依賴居家醫療設備、醫療設備閘道器或院內系統自動串接。

## 2. 目標與非目標

### 2.1 目前目標

- 建立可信、可追溯且能跨裝置同步的寵物健康紀錄。
- 支援一位使用者照護多隻寵物，以及多人共同照護同一隻寵物。
- 降低漏服、重複服藥及提醒建立失敗的風險。
- 以簡潔的摘要與趨勢呈現健康變化。
- 讓飼主在同一寵物履歷中查看生活資料與具明確來源的院方就醫資料。
- 讓醫院以低導入成本的 Web Portal 手動上傳文件與結構化檢查結果。
- 為未來取得明確同意後的模型訓練保留資料來源與版本化能力。
- 讓失主與目擊者以概略區域及私人圖片建立犬隻協尋案件，並為日後可追溯的相似候選比對保留資料契約。

### 2.2 非目標

- 不根據單一紀錄或照片宣稱疾病診斷。
- 不推薦藥名、劑量或療程；用藥內容應來自獸醫師指示。
- 不把面試用未校準模型分數描述為正式 AI 準確率、健康判斷或臨床能力，也不把 BLE、積分或協尋原型描述為已可用服務。
- 不將營運必要同意視為模型訓練同意。
- 不把飼主上傳、OCR 草稿或系統整理冒充院方或獸醫師確認。
- 不要求合作醫院在第一階段更換院內系統或串接醫療設備。

## 3. 使用者與權限

| 角色 | 主要能力 |
| --- | --- |
| 飼主 `owner` | 建立及編輯寵物、管理照片、健康紀錄、用藥、預防照護與共同照護邀請 |
| 可編輯照護者 `editor` | 查看寵物資料，新增及編輯獲授權寵物的照護資料與檔案 |
| 僅查看照護者 `viewer` | 查看獲授權寵物資料，不可新增、修改或刪除 |
| 醫院管理者 `clinic_admin`（規劃） | 管理已驗證醫院的人員與該院提交資料；不可因機構身分自動查看所有寵物 |
| 院方人員 `clinic_staff`（規劃） | 在有效飼主授權內建立草稿、上傳文件與輸入檢查結果 |
| 獸醫師 `veterinarian`（規劃） | 只有在資格、所屬機構及覆核時間可追溯時才能標示獸醫師覆核 |
| 未登入使用者 | 僅可使用登入、註冊、驗證提示與密碼重設流程 |

所有資料存取以 Supabase Row Level Security 為最後權限邊界，前端隱藏按鈕不能取代資料庫授權。生活照護的 `viewer/editor` 不自動取得醫療文件存取權，必須由飼主另行授權。

## 5. 核心需求與流程

### 5.1 帳號與首次進入

1. 使用者以 Email、密碼與暱稱註冊。
2. 未驗證 Email 時顯示提示及重新發送入口。
3. 登入後載入自己擁有及獲授權的有效寵物。
4. 沒有寵物時，必須建立寵物或以邀請碼加入共同照護。
5. 成功取得至少一隻寵物後才進入首頁。

### 5.2 寵物與頭像

- 寵物欄位包含名字、物種、品種、性別、絕育狀態、生日、體重、每日餐數及飲水目標。
- 建立寵物前須再次確認生日；建立後一般 App 操作不可修改生日，首頁年齡由生日即時計算，不另存年齡欄位。
- 寵物選擇器與資料頁優先顯示資料庫 `avatar_path` 的短效簽名圖，其次為 `avatar_icon`，最後才使用預設圖。
- 封存使用 `archived_at`，不可為了介面簡化而破壞健康歷史。

### 5.3 新增生活紀錄

1. 使用者從快速記錄選擇類型與寵物。
2. 選擇便便時，App 先顯示「拍攝記錄」與「手動記錄」兩種方式。
3. 手動記錄顯示結構化欄位，提交後寫入 `care_records`；拍攝記錄沿用目前寵物，建立具使用者、寵物、拍攝時間與時區的 observation，縮放並重新編碼為 JPEG 後上傳私人 Storage，再進入辨識流程；推論用途不等於模型訓練同意。
4. App 顯示各手動記錄類型需要的欄位與單位。
5. 飲食量與飲水量只接受大於 0 的正整數；無效時阻止提交並顯示提示框。
6. 寫入成功後更新摘要、時間軸與趨勢；失敗時保留輸入並可重試。
7. 排程用藥不得由快速記錄重複建立，須從提醒完成。

### 5.3.1 離線生活記錄

1. 第一階段只允許 `meal`、`water`、`stool`、`urine` 離線新增；疫苗、驅蟲、用藥完成、照片、寵物／權限變更及遛狗開始不得進入此 outbox。
2. 支援的生活記錄先保存於目前 Auth user 與 profile 範圍內的本機 outbox，畫面顯示等待同步、同步中或同步失敗。
3. 使用者第一次啟用時選擇自動或手動同步，之後可改為自動、僅 Wi-Fi 或手動；App 開啟、回前景及網路恢復時依設定重試。
4. 每筆資料保存裝置事件時間、IANA 時區及唯一請求鍵。Supabase 另寫入實際接收時間與登入 actor，不把裝置時間冒充伺服器即時量測。
5. 只有收到相同 `client_request_key` 與 `recorded_by` 的精確 acknowledgement 後才刪除本機 outbox；任何錯誤、逾時或回覆不一致都必須保留本機資料。
6. 每次重試重新檢查 RLS 與 editor／owner 權限；viewer、已撤銷照護者及其他帳號不得同步。
7. 同一請求鍵重送不得產生重複記錄；同一鍵搭配不同寵物、種類或事件時間必須拒絕。

### 5.3.2 便便存在辨識（實驗版）

1. 支援 App 即時相機拍攝；測試階段可用 feature flag 開啟相簿辨識入口。兩種方式必須分別記錄為 `live_camera` 與 `gallery_upload`，相簿舊圖不得冒充即時採集，且其 `captured_at` 只代表選取時間。
2. App 先透過已登入的 Edge Function 建立 `stool_observations`，即時拍攝會把畫面上的引導框反算至原始照片，相簿入口則取中央正方形；兩者都產生符合 `stool-roi-768-square-v1` 的 `768×768` JPEG ROI 後上傳至私人 `stool-media`，框外原始照片不會由此流程上傳，影像不得使用永久公開網址。
3. Edge Function 驗證使用者及寵物權限、從 Storage 取圖，並以伺服器端權杖呼叫 Cloud Run；模型端點與權杖不得放入 App。
4. 訓練 release、App ROI 與新版推論共同使用 `stool-roi-768-to-imagenet-224-v1`；每次結果保存模型版本、實際前處理版本、原始未校準分數、門檻版本、延遲與原始回應，供追溯與後續評估。舊版非 `768×768` 輸入必須標為 legacy，不得與新版評估混合。
5. 二元模型以兩類 softmax 較大值產生 `present` 或 `absent` 候選，但分數未校準。資料庫原型政策 `prototype_present_candidate_to_placeholder_v1` 讓 `present` 完成辨識並進入 App 成功佔位頁，`absent`／`uncertain` 才設為 `awaiting_human_review`；這不是正式門檻、人工確認或健康結論。
6. 只有登錄為 reviewer 的帳號能從 App 的審核入口領取 `absent`／`uncertain` 盲審工作；佇列不向審核者顯示模型候選或分數，圖片網址有效五分鐘，人工標籤只允許 `present`、`absent` 或 `not_assessable`。
7. 網路、Storage 或推論失敗須保存為可辨識的失敗狀態並允許重試，不可顯示為「沒有便便」。
8. 本階段不辨識軟硬、顏色、形狀或疾病，不提供醫療解讀；模型與分數尚未使用 Smart Pet Life 真實手機資料完成校準或正式驗證。

### 5.4 查看及修改紀錄

- 每日摘要的紀錄詳情與快速記錄使用一致的欄位語意。
- 使用者可修改內容或刪除紀錄；原始發生時間 `occurred_at` 不可修改。
- 修改成功必須寫回資料庫並重新整理摘要與趨勢。
- 圖表目前只呈現資訊；點擊折線、長條或資料點不得改變日期或導航。

### 5.5 共同照護邀請

1. 飼主輸入受邀 Email 並選擇 `viewer` 或 `editor`。
2. 系統建立有期限的邀請碼與 QR code。
3. 未註冊 Email 可先保留邀請，對方以相同 Email 註冊後接受。
4. 已是照護者、重複待接受邀請、Email 格式錯誤或邀請自己時，必須顯示可理解的提示，不可無反應。
5. 接受、撤銷、過期及權限不足均須有明確完成或錯誤狀態。

### 5.6 預防照護

- 疫苗目前固定每 12 個月；驅蟲可選 1、2 或 3 個月。
- 標記完成時，資料庫在同一交易中新增照護紀錄，並由實際完成日計算下一次日期。
- UI 顯示最近完成日、下次到期日與倒數，不把到期提示描述成醫療診斷。

### 5.7 用藥計畫與提醒

1. 輸入藥物名稱、每次劑量正整數、受控單位、每日 1 至 3 次時間、起訖日期、服用時機與備註。
2. 時間使用滾輪；下拉與滾輪覆蓋在最上層，點框外只關閉選單，不關閉建立頁。
3. 後一次時間須比前一次晚至少 5 分鐘，系統不得自動排序掩蓋錯誤。
4. 頁首固定於頂部；有未儲存內容時按返回需二次確認。
5. 以 RPC 在同一交易建立計畫及全部提醒，使用 `client_request_key` 防止重複提交。
6. 完成按鈕於預定時間前 30 分鐘開放；完成時保存實際服用時間並建立照護紀錄。
7. 到下一次提醒時，未處理的前一劑改為 `overdue`，詢問是否實際服用；回答後記為補登完成或 `skipped`。
8. App 啟動、回前景及目前的週期刷新會同步提醒；正式背景推播仍待實作。

服用時機使用明確選項，例如「飯前 1 小時」「隨餐」「飯後立即」「飯後 2 小時」「睡前」，並提醒依獸醫師或藥袋指示，不由 App 推薦。

### 5.8 遛狗打卡

1. owner 或 editor 開始前必須先向伺服器取得該寵物的遛狗使用權；viewer 不可開始。
2. 同一隻寵物已有有效遛狗時，其他共養者不可開始，介面顯示目前照護者暱稱及開始時間。
3. 遛狗中顯示時間、路程、平均速度、約略熱量與地圖；支援暫停／繼續，暫停期間仍保留並續租使用權。
4. 途中便便及尿尿需二次確認以避免誤觸，並在完成時寫入生活紀錄；便便保留拍攝入口。
5. 完成後顯示含地圖的分享卡供截圖或分享；雲端只保存摘要及排泄事件，不保存原始 GPS 點或路線幾何。
6. App 或網路中斷超過租約期限時自動暫停；恢復時必須重新取得使用權，避免共養者同時遛同一隻寵物。
7. 開始時先取得可接受的首次定位，成功後才占用共養租約並開始計時；12 秒內無法定位時顯示可重試錯誤，不得建立活動或租約。
8. 進入遛狗頁不得等待背景定位設定；背景能力不足時以前景定位繼續，並清楚告知鎖屏或切換 App 的限制。

### 5.9 獸醫院就醫資料協作（資料層及飼主唯讀畫面已實作）

1. 飼主在 App 明確選定寵物與分享範圍，產生短效、一次性授權碼或 QR code。
2. 已驗證醫院人員登入 Portal 後兌換授權；過期、已使用、撤銷或寵物不符時必須拒絕。
3. 院方建立就醫事件，保存實際就醫時間、時區、醫院、建立者與來源。
4. 院方上傳原始文件並輸入檢查值、單位、院方參考區間及原始旗標；上傳與發布失敗必須可重試且不得顯示為完成。
5. OCR 或批次匯入只能建立草稿，經有效院方人員確認後才能標示 `clinic_submitted`。
6. 更正以新版本取代舊版，保留原始證據、修正原因、修正者與時間。
7. 飼主可在醫療中心依目前寵物查看已發布的就醫文件，以及已確認／修正的檢查數據、來源及版本；發布通知尚未完成。
8. 飼主可撤銷醫院的未來存取；撤銷不虛構已下載副本已被刪除。
9. 飼主自行上傳的資料固定標示未驗證，不得冒充院方或獸醫師確認。
10. 生活動態不自動顯示醫療詳細內容；任何分享都必須明確選擇接收者及範圍。

完整資料模型、權限、失敗狀態與驗收條件見 [獸醫院協作平台技術設計](./VETERINARY_COLLABORATION_DESIGN.md)。

### 5.10 犬隻協尋 MVP

1. 已登入使用者可在「協尋」頁瀏覽 `active`／`resolved` 走失與目擊案件；草稿只供建立者查看。
2. 失主只能替自己擁有且未封存的犬隻建立走失案件；目擊案件不能綁定或冒用既有寵物 ID。
3. 刊登流程先建立冪等草稿，再將重新編碼的照片上傳私人 `pet-search-media`，確認全部 Storage 物件存在後才透過受控 RPC 在同一交易發布。
4. 走失案件須提供 3–6 張照片，且在 `front | back | left | right` 中至少有三個不同角度；目擊案件可提供 1–3 張，位置 0 的封面必須為 `live_camera`，相簿只能作補充。
5. 目擊封面由上傳者回報 `suitable | limited`；「正臉與大部分身體清楚」是建議品質而非安全硬性門檻。畫面必須提示保持距離、不要追趕或冒險靠近。
6. `live_camera` 與上傳者品質回報只保存來源事實，不能宣稱為防偽、事件真實性或身分認證；未接入版本化品質模型前不得標成 AI 判定。
7. 公開內容只包含使用者選擇的照片、概略區域、事件時間、品種／性別快照與外觀描述；第一版不收公開電話、門牌或精確座標，也不處理懸賞或金流。
8. AI 候選只對走失案件的失主可見，保存模型、前處理、分數種類、排名及人工確認狀態；相似分數不是同一隻犬的機率，系統不得自動確認身分。
9. 失主可標記「可能是牠／不是牠」，並在尋回後結案；完成頁保留恭喜與感謝內容，不自動跳轉。
10. MPDD baseline artifact、容器化推論契約、測試 Supabase shadow pipeline 與台灣 Cloud Run 端點已接通；2026-09-01 完成 7 筆案件／19 張影像推論並保存 6 筆私有配對，公開候選與通知維持 0。台灣實景 Top-K 驗證、公開候選啟用與系統推播尚未完成。正式資料模式不得以示範資料或假分數替代模型候選。
11. 案件另有一套防冒領驗證與人工線索機制，用於處理「有人聲稱犬隻在自己身邊」的情況。其設計細節屬於非公開範圍，未收錄於這份展示用文件。
16. 無關登入者與匿名使用者不能讀取人工線索關係，App 不可直接新增或更新線索表；重試不得產生重複線索，發布失敗不得留下孤立關聯。
17. shadow 工作使用私有模型版本、PGMQ、推論血緣及 256 維 cosine embedding；結果只能寫入私有 match run，並將案件標記為 `shadow_completed`，不得建立公開候選或通知。
18. 案件結束後必須取消未完成工作並停止搜尋該案件向量；營運圖片固定 `training_eligible = false`，不可因推論或失主判斷轉為訓練資料。

## 6. 資料與業務規則

- 實際資料庫、已部署 migration 及 `mobile/src/types/database.ts` 為現況事實來源。
- 業務主鍵固定為 `類型前綴-8 位大寫十六進制`，例如 `USR-7A3F91C2`、`PET-02BD14E8`；建立後不可修改。
- Supabase Auth UUID 只保存於 `profiles.auth_user_id` 作登入對照，不作 App 業務外鍵或管理畫面識別碼。
- 每筆寵物業務資料保留 `owner_id` 與 `pet_id`；共同照護權限不取代原飼主。
- `occurred_at` 是事件發生時間，`received_at` 是伺服器接收時間，`created_at` 是資料列建立時間，三者不可混用。
- 離線生活記錄使用 `capture_mode = offline`，並保存 `recorded_by`、`client_request_key` 與 `recorded_timezone`；它仍是 owner／caregiver 回報，不是裝置量測或獸醫覆核。
- 記錄保留來源：手動、用藥提醒、遛狗追蹤或 AI 驗證；系統推論不得冒充飼主陳述或獸醫審核。
- 飲食與飲水 `amount` 必須為大於 0 的整數。
- 用藥劑量以數值加受控單位保存；舊 `dose` 只作相容顯示。
- 照片及附件只保存私人 Storage 路徑，不把 base64 或永久公開 URL 寫入業務 JSON。
- 協尋圖片上傳只供營運比對，不自動取得模型訓練資格；案件相似候選必須保存模型與前處理版本，且失主人工判斷不得冒充模型或專家真值。
- 防冒領題組、回答與結果同樣只供營運風險控制，固定與訓練資料流程隔離；失主設定題組不是訓練同意。
- 目前 `care_record_kind = medical` 在 App 中實際代表驅蟲，不得直接解釋為正式就醫；正式病例規劃使用獨立的就醫、文件及檢查結果資料表。
- 飼主回報、共同照護者回報、院方提交、獸醫師覆核與系統整理必須保留不同來源，不得互相升級。
- 健康資料保留期限、刪除、模型訓練同意及跨境處理仍需政策與法律審查，本文件不臆定期限。

## 7. UI、狀態與無障礙

- 資料頁須處理載入、空資料、成功、驗證失敗、權限不足、網路錯誤及重試狀態。
- 待同步記錄須有文字狀態，不能只靠顏色；同步完成前暫不提供雲端編輯，避免本機與伺服器版本分叉。
- 下拉選單與時間滾輪使用頂層 overlay，不推動原頁布局；點擊框外關閉 overlay。
- 時間滾輪顯示目前焦點及前後各一個單位，超出範圍的位置留白。
- 重要狀態使用文字、圖示與顏色共同表達，不只依賴顏色。
- 觸控目標、字級、對比、鍵盤避讓、安全區及 VoiceOver／TalkBack 標籤須實機驗證。
- 繁體中文為目前主要介面；後續簡體中文需驗證文字長度與區域用語。
- 建立及編輯頁不得因點擊背景而遺失整頁輸入。
- 底部主要頁籤固定為「首頁／紀錄／醫療／協尋／我的」；醫療與協尋保留底部導覽，相機流程採全螢幕並提供清楚的返回與放棄照片確認。

## 8. 健康安全與隱私

- 趨勢只描述增加、減少或偏離平常等觀察，不顯示疾病名稱或確定性結論。
- 未來警示須區分日常留意、建議聯絡獸醫與緊急就醫，並提供症狀及時效依據。
- 目前沒有合格獸醫審核者；需要專家真值的資料只能標示 `awaiting_expert_review`。
- 院方檢查值只忠實呈現院方提供的單位、參考區間及旗標；平台不根據單一結果產生疾病結論。
- 模型訓練同意須獨立、特定用途、可撤回、具版本與稽核紀錄；未同意資料不得進入訓練集。
- 目前 Supabase 位於新加坡、Cloud Run 位於台灣；照片跨區傳輸的法源、告知、保存及刪除政策在正式上線前須完成資料治理審查。
- 台灣、中國大陸及其他地區的資料落地、跨境、刪除與保存政策，須由合格法律顧問及部署負責人核准。

## 9. 非功能性需求

- 所有傳輸使用 HTTPS；App 只包含 publishable key，不得包含 `service_role` 或其他秘密。
- RLS、RPC 與 Storage policy 須覆蓋匿名、飼主、viewer、editor 及無關登入者。
- 用藥計畫等複合寫入須具交易性與冪等性。
- 頁面不得以本地假資料覆蓋雲端狀態；同步失敗需顯示並可重試。
- Realtime 只增強即時體驗；回前景仍需重新查詢以確保正確性。
- 便便辨識呼叫須由 Edge Function 代理；Cloud Run 權杖只存在伺服器秘密，公開 App bundle 與 Git 不得包含該值。

## 10. MVP 驗收條件

- 暱稱與寵物資料可在重新登入後由雲端還原。
- 寵物選擇器正確使用資料庫頭像。
- viewer 無法寫入；editor 與 owner 可在授權範圍寫入；無關帳號無法讀取。
- 飲食／飲水輸入 0、小數、負數或非數字時不可送出，並顯示提示。
- 修改或刪除紀錄後摘要與趨勢可刷新，且 `occurred_at` 不變。
- 重複照護者、重複邀請及未註冊帳號等結果均有清楚提示。
- 用藥時間未嚴格遞增時不可建立；快速連點不產生重複計畫。
- 完成提醒保存實際服用時間並關聯照護紀錄；漏服可區分補登完成與跳過。
- 點擊健康圖表不改變日期或導航狀態。
- 私人圖片不能以未簽名公開網址存取。
- 同一隻寵物不能同時存在兩位共養者的有效遛狗租約；完成後摘要與途中排泄可在記錄頁讀取。
- 首次定位失敗時不開始計時、不建立租約，使用者可返回或重試；背景定位不可阻塞進入遛狗頁。
- 醫療中心依 RLS 讀取資料：無醫療授權的照護者不能讀取病例，生活照護 `viewer/editor` 不等於醫療權限；文件修正保留舊版，飼主上傳不能被誤標為院方確認。
- 離線生活記錄在斷網與 App 重啟後仍可見；自動、僅 Wi-Fi、手動模式符合設定；重送只建立一筆；viewer 與不支援種類被伺服器拒絕；失敗時本機資料不刪除。
- 便便拍攝可建立 observation、上傳私人 JPEG 並顯示未校準原始分數；二元模型候選 `present` 進成功佔位頁，`absent`／`uncertain` 進人工審核，且推論失敗不會被顯示為 `absent` 或投放成功。
- 協尋草稿只對建立者可見，公開案件可由已登入使用者瀏覽，其他帳號不能查看失主的 AI 候選或代替失主結案；刊登失敗不得留下已公開但沒有圖片的案件。

## 11. 已知限制與路線圖

### 11.1 已知限制

- Session 目前使用 AsyncStorage 持久化，以支援 App 重啟後在同一帳號續傳；卸載或清除 App 資料會刪除尚未同步的本機 outbox。
- 本機 SQLite 尚未使用 SQLCipher；若後續把正式醫療內容納入離線保存，須先改用 Development Build、加密儲存並完成威脅模型與區域隱私審查。
- 系統級本機／推播通知尚未完成，背景狀態不能保證準時刷新提醒。
- 照護紀錄主要以手動刷新同步，尚未全面使用常駐 Realtime。
- 共同照護重複成員的提示仍需以實機回傳格式持續驗證。
- 實體 iPhone 的 Expo Go 不支援正式背景定位；鎖屏或切換 App 的完整遛狗記錄需使用 Development Build。
- 醫療中心目前不提供上傳、編輯、分享設定或發布通知；用戶端五分鐘短效下載尚未經下載閘道寫入完整伺服器端稽核。
- 便便存在辨識使用 `stool-presence-mobilenet-v2-reviewed-20260826-experimental`；新版拍攝、訓練與推論的共同前處理為 `stool-roi-768-to-imagenet-224-v1`，舊版全圖輸入另標示為 legacy。softmax 相對分數仍未校準，現有測試集無便樣本只有 43 張，且尚未完全排除跨 split 近似影像，因此 `present` 成功佔位路由只可作原型測試。
- 犬隻協尋已接通測試 Supabase shadow 佇列、Edge worker 與台灣 Cloud Run；Cloud Run 在網路層公開可達，但 embedding 端點要求 64 字元服務權杖，並限制 max instance 1／concurrency 1。7 筆既有工作與 19 張影像已完成，6 筆配對只保存在私有 schema，公開候選與通知仍為 0。模型尚未通過台灣實景評測、未對使用者啟用，也不支援貓咪或系統推播。
